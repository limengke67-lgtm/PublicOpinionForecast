# 预测验证与降本实验工作台

本次改动在原有 MiroFish 上增加可量化验证和运行优化。页面入口为 `/research`，首页和仿真运行页均有链接。

第三项“滚动自适应预测”已接入，最新闭环、真实数据回放与验收说明见 [闭环验收与真实事件运行手册](./闭环验收与真实事件运行手册.md)。

当前实现验证的是**未来各时间桶的发帖与评论数量**，以及有可信标注时的负面占比。报告写得是否合理、单个事件是否一定发生，不由这些指标直接证明。项目目前没有真实舆情数据，内置案例全部明确标注为合成演示。

## 本机启动

在项目根目录运行：

```powershell
npm run dev:research
```

打开 <http://127.0.0.1:3000/research>，点击“用合成示例跑通验证”。此模式不需要 API Key，后端会拒绝原有模型、图谱等接口，支持数据导入、预测冻结、误差计算、导出、账本和配置管理。

已按原有锁文件安装根目录、前端依赖和后端独立 `.venv`，没有新增 Python 或 npm 依赖。Python 3.11 解释器、安装工具及缓存位于 `backend/.python`、`.tools`、`.uv-cache`，均被 Git 忽略。Windows 中文路径使用非 editable 安装，避免 `.pth` 编码问题。

完整推演沿用原有模型、Zep 配置及 API：停止离线服务后，配置项目已有的 `.env`，使用 `npm run dev`。真实推演会产生供应商费用，本次开发没有调用这些付费接口。

## 数据格式与验证流程

CSV 表头为 `timestamp,volume,negative_ratio`。JSON 为包含同名字段的对象数组。`negative_ratio` 可省略。

```csv
timestamp,volume,negative_ratio
2026-01-01T08:00:00+08:00,10,0.2
2026-01-01T09:00:00+08:00,15,0.3
2026-01-01T10:00:00+08:00,20,0.4
2026-01-01T11:00:00+08:00,18,0.35
```

- `timestamp` 是时间桶结束时刻，必须包含时区。最后一个已完整观测桶的结束时刻就是预测截止时间；第一个预测桶结束于“截止时间 + 桶长”。服务器统一转为 UTC。
- `volume` 是同一平台、同一采样口径的发帖与评论数，必须为非负有限数值。浏览量、点赞量、热搜排名不能混为这个指标。
- `negative_ratio` 范围为 0～1，须来自可信的人工或已有标注。
- 当前支持 1～168 小时的整数桶长、1～500 桶预测窗口、最多 10000 行 / 10 MB 文本。时间桶必须连续、无重复；缺失记录不会自动当作零。

操作步骤：

1. 导入观测数据，选择截止时间、桶长和预测桶数，至少保留 3 桶早期观测。可以仅上传早期数据，也可以上传包含后续值的完整数据。
2. 后续真实值单独保存，不进入常规案例响应和早期材料导出。可填写截止前背景材料；使用者须核验背景、案例名及来源中没有未来信息。
3. 完整模式中点击“用早期材料创建推演”，系统将唯一的早期材料、规范化需求与项目绑定。完成准备后运行原有仿真，轮次必须覆盖预测窗口。
4. 选择仿真实例、平台及热度映射方式，保存预测快照。也可导入外部预测，或使用“保持最近值”“近 3 桶均值”两个免费基线。
5. 如只有早期数据，等预测冻结后再补充真实后续数据。系统拒绝覆盖早期值或已提交的真实值；数据修订应新建案例。
6. 计算误差，勾选同案例预测进行对照。CSV 导出逐桶真实值和预测值；JSON 包含指标、指纹、来源元数据和当时查询到的用量账本。

预测保存为独立快照，记录内容 SHA-256；后续评估校验指纹，拒绝直接修改后的预测。指纹用于发现内容变化，不是第三方时间戳或不可伪造的存证。历史回测、外部预测和用户输入都需要额外核验是否接触未来信息，不能仅凭“冻结”声称完全杜绝数据泄漏。

## 仿真输出如何映射

从所选平台的 `actions.jsonl` 提取成功的 `CREATE_POST` 和 `CREATE_COMMENT`，按仿真轮次映射到预测时间桶。第 0 轮初始化、失败动作、点赞等不计入。未完成足够轮次、失败或正在运行的实例不能作为完整窗口评分。

- **原始计数**：直接比较仿真发帖 / 评论数。必须保证仿真人口规模与真实采样范围可比。
- **早期锚定**：用“截止前最后一桶真实量 ÷ 首个仿真预测桶数量”作为缩放因子。只使用早期真实值，衡量相对热度形状；首桶为零时拒绝锚定。这不是绝对传播规模的完整校准模型。

系统保留输入和配置指纹、日志指纹，并记录图谱是否由同案例早期材料建立且未参与过推演。复用已写入模拟未来的图谱、旧项目或未绑定材料的结果会标为探索性。严格回测应为每次独立实验建立新的早期材料项目和图谱。即使本地记录通过，材料本身的真实性与发布时间仍需人工核验。

动作日志没有可靠的情感标注，因此不会自动编造负面比例。只有预测和真实值都提供比例的桶才计算对应 MAE，并显示覆盖桶数。

## 指标含义

| 指标 | 用途与边界 |
| --- | --- |
| MAE / RMSE | 平均误差与对大误差更敏感的误差，越低越好 |
| WAPE | 绝对误差总和 / 真实量总和，可能超过 100%；真实总量为零时留空 |
| SMAPE | 对称相对误差，两个值均为零的桶记零 |
| 相关系数 | 曲线共同变化程度；常量曲线无定义，留空 |
| 峰值时间差 | 峰值所在桶的时间距离；常量曲线留空，多个最高峰取最早一个 |
| 相对基线 MAE 改进 | `1 - 本预测 MAE / 基线 MAE`；负值表示更差，基线零误差时留空 |

不能使用 `100% - WAPE` 作为“预测准确率”。单次事件优于基线也不代表普遍预测能力，毕业论文应使用独立事件、多次重复和预先固定的实验方案。

## 降本与提速的具体范围

1. **复用画像准备结果**：同模型、接口、凭据指纹、语言、提示词实现和输入完全一致时，复用已验证的画像结果，保存 7 天。并发重复请求在单后端进程内合并；失败后的兜底画像不缓存。
2. **并行生成独立配置**：时间配置、事件配置及不同角色批次独立请求，优化模式默认最多 4 个并行任务，结果按原顺序汇总。对照模式串行执行相同请求。
3. **避免重复付费操作**：页面重新进入时恢复现有仿真；准备和报告的在途任务合并；同一次运行的完整报告优先复用。新运行不会复用旧运行的报告。
4. **可调角色决策并发**：每平台可配置 1～128，默认保留原有 30。更高并发不减少 Token，是否更快取决于供应商限流与延迟。
5. **固定实验抽样条件**：每个平台使用独立随机数生成器，避免双平台并发调度相互改变抽样序列。固定种子只控制角色抽样，不保证云模型输出完全相同。

当前降本主要针对重复准备和重复操作，首次运行仍需要正常的模型调用。每轮智能体独立决策保持原有模型和提示词，不缓存；本次没有引入未经验证的低价模型替代或减少角色 / 轮数。并发主要减少等待，不能等同于单个模型推理能力提升。

复用画像会固定一次初始化；需要独立重新采样画像的实验应选择对照模式。若比较固定初始化下的两种策略，应记录或复用同一组画像，并单独计量共同初始化与运行成本。

## 用量、费用和预算

OpenAI 兼容 SDK 的同步和异步 Chat Completions 请求均记录到本地 SQLite 账本，覆盖原有应用请求及仿真子进程中 CAMEL 发起的请求。账本不保存提示词、模型响应或 API Key；准备缓存另存画像结果。

费用按**元 / 百万 Token**自行填写每个实际模型的输入、输出及可选缓存输入价格。价格取自你的供应商账单，不预设可能过时的价格。

```text
估算费用 = ((输入 - 缓存命中输入) × 输入单价
           + 缓存命中输入 × 缓存单价
           + 输出 × 输出单价) / 1000000
```

没有单价、失败请求没有可靠 usage、流式返回尚未读取 usage 等情况均显示无法完整估算，不伪装成零费用。这里的金额不含 Zep，且不等同最终供应商账单。SDK 内部的网络重试也未单独计数。

按 `proj_…` 查看本体生成，按 `sim_…` 查看准备与报告，按唯一的 `run_…` 查看一次运行中的角色决策 / 采访。验证结果聚合这三个关联范围；同项目或同实例的多次准备和报告会累计，应使用独立实例进行干净的成本对照。账本时间窗反映模型请求跨度，不等同图谱构建、排队等全部端到端时间。

请求次数上限通过 SQLite 事务在发起 SDK 请求前原子预留。金额阈值在已知费用到达阈值后阻止新请求；并发在途请求仍可能超额，因此不属于绝不超支的硬预算。金额阈值要求已配置单价且已完成请求可完整计价。

智能体库即使吞掉预算异常，后续轮次检查也会识别拒绝记录并将不完整仿真标为失败。预算值为 0 表示不限制。生产运行前建议先配置一个较小的请求次数上限。

## 离线验证与复现

```powershell
cd backend
.\.venv\Scripts\python.exe -X utf8 -m pytest tests -q
.\.venv\Scripts\python.exe -X utf8 scripts\benchmark_efficiency.py --output ..\docs\benchmarks\offline-efficiency.json
cd ..\frontend
npm run build
```

[离线基准结果](./benchmarks/offline-efficiency.json)使用确定性返回值及固定等待时间，且隔离账本和缓存，无真实 API 请求。它验证重复准备请求减少、独立任务并行且输出和角色顺序一致，**不能作为真实 API 省费比例、真实推演速度或预测效果的实验结果**。

真实实验建议先收集具有可靠时间戳的多个事件，固定统计口径、截止时间、预测窗口、模型、初始化、轮次及随机种子，分别运行对照与优化方案。联合比较误差、Token、费用和总耗时，完成重复实验后再判断效果是否保持、实际节省多少。

本机业务验证结果：173 项后端测试通过，前端生产构建通过，桌面和手机页面的评分、对比、导出及设置显示正常，浏览器无控制台错误。额外运行原仓库根目录的 Star History 测试时，两项符号链接测试因 Windows 缺少创建符号链接的权限（WinError 1314）失败；没有为此修改系统权限或无关功能。前端仍有原有的包体积和混用动态 / 静态导入构建提示。
